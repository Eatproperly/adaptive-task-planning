# 计划的最小可用结构

用用户的语言交付。少量任务采用简短文本，分支较多时采用文本树或 Mermaid；依赖用带任务编号的关系说明。不要为了画图搭建应用。下面是内容规范，不是必须逐栏展示的长表。

## 任务简报

记录总目标、重要性与用户理由、模式、最低与理想结果、硬性底线、范围与非目标、投入上限、相关经验，以及待验证假设。说明当前版本和最近更新原因。

## 全局树与关系

父节点：编号、目的/成果、对应的总体验收项。
叶子节点：按下方任务卡定义。
远期节点：标待展开，说明目的、预期成果、何时获得足够信息展开。
关系：明确 A 的什么结果会解锁或改变 B/C。共享资源和备选分支单列，避免被误读为完成依赖。

## 可执行任务卡

- 编号及名称：动作 + 对象 + 范围。
- 输入和前置条件：材料、工具、具体前置成果及关键前提编号。
- 行动：用户已理解的具体动作；不要求写成机械的逐点击说明。
- 产出：文件、作品、答案、能力表现或可观察变化。
- 验收：检查方法及通过条件；标出硬性要求。
- 负担：符合需要的时间/精力范围及不确定性，不伪造精确估时。
- 阻碍处理：关键问题出现时的验证、求助或修复办法；可引用前提表。
- 校准依据：用户反馈、已知经验或已校准同类任务。无法判断则待校准。
- 状态及结果：只记录已知信息。

相同输入、规则或前提可以在父节点定义后引用，不必重复堆在每张卡里，但卡片必须能通过明确引用找到上下文。

## 状态规则

| 状态 | 含义 |
| --- | --- |
| 待展开 | 远期结构节点，细节依赖新信息 |
| 待澄清/待校准 | 任务定义或用户可执行性尚不明确 |
| 等待前置 | 定义清楚，但前置成果/资源还未满足 |
| 可执行 | 清晰度、用户能力校准和前置条件均通过 |
| 进行中 | 用户报告正在执行，保留已完成部分 |
| 受阻 | 执行被具体障碍阻断，记录解阻条件 |
| 待验收 | 已有产出，尚未确认符合标准 |
| 完成 | 按约定标准通过，注明基于用户报告或可检查证据 |
| 需返工 | 验收未过或新证据要求重新处理 |
| 取消/被替代 | 保留原因、旧编号及替代任务关联 |

简单任务不必逐个经历所有状态。父节点完成需检查整合成果；不能仅因子节点都完成就自动完成。修改编号时保留旧新映射。

## 前提、变化与下一步

关键前提记录按 premise-recovery.md。重规划记录：触发事件、证据、受影响任务、新旧差异、用户的关键取舍、保留成果及版本号。

每轮结束给出当前可执行项和推荐的下一项，说明推荐原因；同时明确用户下次需要报告的成果或变化。涉及暂停、取消或前提失效时优先突出这些变化，不重复整份计划。

## 两种投入水平示例

以下数字和材料仅为示例，实际需依用户的要求校准。

**重要学习任务：** 用户目标是能独立解指定类型的题。叶子任务可以是“完成指定的三道代表题，核对答案，解释每题方法并订正错误”。关键检查是独立应用，不只是阅读。若第一题就无法开始，先定位卡点再补前置知识。

**够用的作业：** 若用户明确要求只达必交标准，任务可为“依据教师要求完成全部必答项，检查姓名、文件格式与可打开性，在截止前提交并确认收到”。选做与美化可排除，但不得把提交或必答项理解为可只完成六成；不得宣称这一定能拿到六十分。
